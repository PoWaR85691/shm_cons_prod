# Fast Channel

Два процесса на C++17 передают файл через **256-байтный канал в разделяемой памяти**: Producer читает файл, сжимает его и отправляет, Consumer принимает и распаковывает. Это два отдельных исполняемых файла.

---

# 1. Инструкции

## Зависимости (Debian/Ubuntu)

```bash
sudo apt update
sudo apt install cmake clang lld libzstd-dev libzfp-dev doctest-dev make
```

## Сборка

```bash
cmake -S . -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CXX_COMPILER=clang++ \
  -DCMAKE_LINKER=ld.lld \
  -DFAST_CHANNEL_SYNC=spinlock        # или semaphore
cmake --build build --parallel
```

`FAST_CHANNEL_SYNC` выбирает примитив синхронизации процессов: `spinlock` (`std::atomic<bool>`) и `semaphore` (POSIX `sem_t`)

## Тесты

```bash
ctest --test-dir build --output-on-failure
```

## Запуск

```bash
./build/producer bin/source_data.bin        # читает и сжимает
./build/consumer /tmp/restored.bin          # принимает, распаковывает и пишет
```

Аргумент у каждого процесса один - путь к файлу. Остальное задаётся переменными окружения:

| переменная              | значения                                                 | по умолчанию      |
| ----------------------- | -------------------------------------------------------- | ----------------- |
| `COMPRESSION_ALGORITHM` | `none`, `zstd[,<level> = 1]`, `zfp[,<accuracy> = 0.001]` | `zstd`            |
| `WORKERS_COUNT`         | целое >= 1                                               | число процессоров |

После завершения передачи данных программы выводят в консоль

- `original_bytes` - без учета `\n`
- `transmitted_bytes` - число байт, переданных через разделяемую память
- `elapsed_seconds` - время передачи
- `compression_percent` - процент сжатия = `100 * transmitted_bytes / original_bytes`

Потеря данных `loss_percent` вычисляется по формуле средней относительной погрешности при помощи скрипта `python3 loss_percent.py <исходный> <восстановленный>`.

```text
e[i] = abs(out[i] - in[i]) / abs(in[i])
loss_percent = 100 * sum(e) / len(e)
```

## Данные

В каталоге `bin/` лежат файлы в формате из задания — **бинарное представление чисел с плавающей точкой (32 бита) с разделителем `\n`**.

# 2. Документация

## Архитектура

Два процесса, один канал связи - ровно 256 байт в разделяемой памяти. Канал является единственной точкой взаимодействия.

**Producer:** читает файл блоками -> пул потоков сжимает блоки параллельно -> один поток передаёт блоки в канал в том порядке, в каком они успели сжаться.

**Consumer:** один поток принимает кадры из канала -> пул потоков распаковывает блоки параллельно -> один поток пишет блоки в файл строго по номерам, восстанавливая исходный порядок.

Поток в канале состоит из кадров трёх видов: `BEGIN` (номер блока, id алгоритма, размеры), `DATA` (данные блока, до размера слота в кадре) и `END` (конец передачи).

## Выбор алгоритма сжатия

В проекте есть три варианта:

- `none` — передача без сжатия, эталон для сравнения;
- `zstd` — без потерь, быстрый;
- `zfp` — с потерями, рассчитанный именно на массив `float`. Обеспечивает гораздо большую степень сжатия, чем lose-less `zstd`.

## Синхронизация разделяемой памяти

256 байт делятся на небольшой блок управления и слот под данные. Синхронизируют его два примитива из блока управления, работающие как эстафетная палочка (см. "Архитектура"). Реализация задается при сборке:

- `spinlock` - один `std::atomic<bool>`: ждёт активным опросом, экономит 62 байта по сравнению с семафорами и отдаёт их слоту;
- `semaphore` - POSIX-семафор: на ожидании отдаёт ядро планировщику, но занимает больше места и влечет накладные расходы связанные с взаимодействием с операционной системой.

Взаимодействие процессов:

```text
Producer:  lock(empty) -> записать слот  -> unlock(full)
Consumer:  lock(full)  -> прочитать слот -> unlock(empty)
```

Каждый замок берёт только одна сторона и отпускает только противоположная, поэтому владение слотом строго чередуется. Сегмент создаёт тот, кто пришёл первым; готовность определяется его размером, а гонка при подключении исключена блокировкой файла.

Изначально при инициализации памяти: `empty` = 1, `full` = 0.

## Результаты измерений

Стенд: AMD Ryzen 7 7700 (8 физических ядер, 16 потоков), `bin/source_data.bin`, по 16 потоков на процесс, если не указано иное.

**Влияние примитива синхронизации** (`zstd`):

| примитив    | время  |
| ----------- | ------ |
| `semaphore` | 1.22 с |
| `spinlock`  | 0.03 с |

Спин-блокировка быстрее за счет снижения накладных расходов при переключении контекста операционной системой при использовании семафоров.

**Влияние алгоритма сжатия** (`semaphore`):

| алгоритм       | передано | сжатие | время  | потери |
| -------------- | -------- | ------ | ------ | ------ |
| `none`         | 52.4 МБ  | 0%     | 1.31 с | 0      |
| `zstd` (1)     | 46.9 МБ  | 10.5%  | 1.22 с | 0      |
| `zstd` (2)     | 46.9 МБ  | 10.5%  | 1.28 с | 0      |
| `zstd` (10)    | 46.9 МБ  | 10.5%  | 1.19 с | 0      |
| `zfp` (0.0001) | 31.1 МБ  | 40.8%  | 0.86 с | 0.02%  |
| `zfp` (0.001)  | 24.5 МБ  | 53.3%  | 0.62 с | 0.58%  |
| `zfp` (0.01)   | 19.6 МБ  | 62.6%  | 0.50 с | 4.04%  |
| `zfp` (0.1)    | 14.7 МБ  | 72.0%  | 0.41 с | 22.8%  |

- Канал - узкое место. Степень сжатия сильно влияет на скорость передачи.
- Увеличение степени сжатия `zstd` практически не влияет на размер сжатых данных.
- Оптимальная точность для `zfp` = 0.001 - баланс между производительностью и точностью.

**Влияние алгоритма сжатия** (`spinlock`):

| алгоритм      | передано | сжатие | время   | потери |
| ------------- | -------- | ------ | ------- | ------ |
| `none`        | 52.4 МБ  | 0%     | 0.034 с | 0      |
| `zstd` (1)    | 46.9 МБ  | 10.5%  | 0.034 с | 0      |
| `zfp` (0.001) | 24.5 МБ  | 53.3%  | 0.067 с | 0.58%  |
| `zfp` (0.01)  | 19.6 МБ  | 62.6%  | 0.059 с | 4.04%  |

Канал перестает быть узким местом, поэтому сжатие не приносит выигрыша.

**Влияние числа потоков** (`spinlock`):

| `WORKERS_COUNT` | `zfp`   | `zstd`  | `none`  |
| --------------- | ------- | ------- | ------- |
| 1               | 0.269 с | 0.056 с | 0.033 с |
| 4               | 0.079 с | 0.039 с | —       |

Увеличение числа рабочих потоков практически не влияет на производительность - все упирается в канал между процессами.

## Компромиссы ради оптимизации

- **Один слот вместо кольцевого буфера** - проще и не требует выделять место под параметры буфера.
- **Спин по умолчанию** - на этих данных в десятки раз быстрее семафора, ценой активного ожидания.
- **Уровень по умолчанию `zstd` = 1** - более высокие уровни уменьшают скорость сжатия без существенного выигрыша по степени сжатия.
- **Точность по умолчанию `zfp` = 0.001** - не слишком быстрее чем при точности 0.01, но гораздо большей точностью.
- **Производительность ценой потери данных (semaphore)** - при использовании семафоров для синхронизации узким местом становится канал между процессами из-за затрат на переключение контекста ядром операционной системы. Алгоритм с потерями `zfp` дает гораздо большую степень сжатия по сравнению с алгоритмом без потерь `zstd`.

## Итоговые выводы

Выбор сжатия данных зависит от скорости канала:

- При медленном канале (`semaphore`) выгоднее сжимать данные. Затраты на компрессию-декомпрессию на передающей и принимающей стороне гораздо меньше, чем передача большего количества данных при низкой пропускной способности.
- При быстром канале (`spinlock`) лучше обойтись вообще без сжатия. Пропускная способность канала гораздо выше, чем скорость компрессии-декомпрессии.
- Если выбирать сжатие, то наиболее оптимальные варианты:
  - если необходимо отсутствие потерь данных - `zstd` со степенью 1;
  - если допустимы потери - `zfp` с точностью 0.001; производительность при выборе `semaphore` в 2.11 раза больше, чем без сжатия, и в 1.97 раза больше, чем при сжатии без потерь алгоритмом `zstd` со степенью 1.
- `spinlock` выигрывает `semaphore` по скорости в 38.5 (без сжатия) за счет минимизации обращений к операционной системе с связанными с этим переключениями контекста.
